# 레이첼 발전 기획 — 내 일을 끝까지 챙기는 개인비서

작성: 2026-09-05 · 검토 기준: `dd3782d2ab10dcc0b6911f2dfe625f98ebeffc3d`

**레이첼의 다음 개선 목표는 “내가 한 번 말하면, 할 일·일정·회의 기록에 정확히 반영되고, 이후 변경과 누락까지 이어서 관리되는 것”이다.** 현재는 기본 CRUD 도구가 있어도 화면의 새 기능과 AI 실행 경로가 달라 이 경험이 끊긴다. 우선순위는 실행 신뢰성 → 기능 접근성 → 개인화된 판단 → 제한된 선제 제안 순서다.

이번 산출물은 기획과 코드 검토다. 앱 코드·운영 데이터·배포는 변경하지 않았다. 로컬 임시 사용자로 도구 계약과 SDK 동작을 재현했으며, 실제 Luna 대화·Google 동기화 장애·음성·푸시의 운영 환경 종단 검증은 하지 않았다. 상세 근거는 [CRUD 감사](AUDIT.md), 완료 조건은 [수용 기준](ACCEPTANCE.md), 실제 도구 목록은 [JSON](tool-inventory.json)에 있다.

## 1. 기획의 전제와 제품 판단

- 사용자는 개인의 할 일·일정·회의록을 자주 사용한다. 협업 관리자·범용 CRM 기능보다 개인의 판단·입력·후속 확인 부담을 줄이는 것을 우선한다.
- 선제 개입 선호에 대한 답은 아직 없으므로 **중요한 누락·충돌만 먼저 알림**을 잠정 기본값으로 삼는다. 사용자가 개입 수준을 명시하면 이 기본값보다 우선한다.
- 사용자가 명확히 요청한 단일 변경은 곧바로 처리한다. 대상을 특정할 수 없거나 파급 범위가 큰 변경만 구체적인 미리보기를 제시한다. 모든 쓰기에 반복 확인을 붙이지 않는다.
- `오늘 할 계획`, `반드시 끝낼 마감`, `캘린더에 잡은 시간`은 서로 다르다. 오늘 하지 못했다고 마감까지 자동으로 미루지 않는다.
- 설정은 사용하면서 필요한 것만 묻는다. 첫 진입에 성격·목표·근무 규칙을 길게 입력시키지 않는다.
- 루나 교체를 먼저 할 근거는 없다. 현재 소스는 chat/extract/summarize/review 모두 `gpt-5.6-luna`이며, 발견한 문제 중 상당수는 도구·저장·조회 경로의 문제다. 먼저 동일 모델에서 실행 계약을 고치고 평가해야 모델 판단 오류와 시스템 오류를 구분할 수 있다. [모델 설정](../../../src/core/llm/models.ts#L7)

## 2. “자유롭게 CRUD 가능”의 목표 정의

현재 9개 모듈 중 6개가 총 37개 AI 도구를 제공한다. 도구 수는 기능 완성도 비율이 아니다. 오늘 계획과 반복 규칙처럼 **쓰기는 되지만 읽기 결과에 빠지는 기능**, 회의 교정처럼 **화면에는 있지만 도구가 없는 기능**, 반복 일정 시리즈 편집처럼 **제품 자체에 없는 기능**을 구분해야 한다.

목표는 사용자가 제품에서 할 수 있는 업무를 레이첼도 같은 서비스와 제약으로 수행하게 하는 것이다. 마이크·브라우저 알림 허용·Google OAuth 동의는 사용자 기기에서 하는 정상적인 권한 경계다. 레이첼은 필요한 버튼과 정확한 상태를 제공한다. 원시 SQL, 인증 키, 내부 작업 큐를 직접 조작하는 범용 도구는 이 목표에 포함하지 않는다.

공통 계약은 다음처럼 작고 명확하게 잡는다.

| 구간 | 필요한 계약 | 사용자가 체감하는 결과 |
|---|---|---|
| 읽기 | 수정 가능한 필드, 버전, 출처, 조회 범위, 다음 페이지, 동기화 시각 | “모두 확인했다”는 말의 근거가 생긴다 |
| 변경 | 명시한 필드만 수정, 실행 직전 버전·제약 검사, 안정된 요청 ID | 재시도와 동시 수정으로 중복·덮어쓰기가 생기지 않는다 |
| 승인 | 대상·변경 내용·영향을 보여준 제안 ID와 승인 연결 | 승인한 내용만 실행되며 버튼 뒤에 실제 처리가 이어진다 |
| 결과 | 자원 유형·링크, 생성/재사용 수, 로컬 저장·외부 반영·대기·충돌 구분 | “저장됐어요”와 “Google에도 반영됐어요”를 구분한다 |
| 복구 | 실행 기록 조회, 안전한 재개, 보관 복원, 변경 필드 기준 Undo | 실패한 작업을 사용자가 처음부터 설명하지 않아도 된다 |

UI와 AI는 같은 업무 서비스를 호출한다. “시간 잡기”는 `일정 생성 → 할 일 링크 수정`을 모델이 매번 조합하게 하지 않고, 기존 `scheduleTask`를 공통 작업으로 노출한다. 이동·취소도 같은 수명주기로 묶는다. 전체 모듈을 다시 쓰는 추상화는 필요 없다. [기존 시간 잡기 서비스](../../../src/modules/tasks/scheduling.ts#L10)

```mermaid
flowchart LR
  U[화면 조작 또는 대화 요청] --> R[현재 상태와 사용자 규칙 확인]
  R --> P[변경안 또는 명확한 단일 명령]
  P --> S[공통 업무 서비스]
  S --> O[실제 결과와 복구 경로]
  O --> F[필요한 후속 확인]
```

## 3. 매일 유용해지는 다섯 장면

| 장면 | 레이첼의 행동 | 최소 UI | 완료 조건 |
|---|---|---|---|
| 아침, “오늘 뭐부터?” | 고정 일정·오늘 계획·마감·가용 시간을 함께 읽고 오늘 끝낼 결과 1~3개를 제안 | 오늘 화면의 기존 브리핑에 `오늘 계획에 넣기`, `시간 잡기` | 마감 없는 계획도 포함. 동의한 계획만 저장. 소요시간 미정은 추정임을 표시 |
| 갑자기 회의가 들어옴 | 겹친 집중 시간과 영향받는 할 일을 찾아 이동 가능한 시간을 제안 | 해당 일정/할 일 옆 한 장의 조정 카드 | 고정 약속은 유지. 이동 전 충돌 재검사. 연결된 할 일도 함께 갱신 |
| 회의 직전 | 지난 결정·아직 열린 내 후속 작업·이번에 확인할 질문을 짧게 정리 | 일정 상세에서 `회의 준비` | 실제 회의 연결과 교정된 출처 사용. 관련 회의를 못 찾으면 없다고 명시 |
| 회의 직후 | 내 할 일, 타인에게 받을 답, 일정, 참고 기록으로 후속 항목을 나눔 | 기존 후속 검토 화면과 같은 편집 가능한 카드 | 담당·마감·분류를 고친 뒤 한 번에 확정. 재시도해도 중복 없음 |
| 하루 마감 | 완료하지 못한 계획 중 마감에 영향을 주는 것만 짚고 재배치 제안 | 오늘 화면 아래 짧은 정리 | 무조건 내일로 이월하지 않음. `내일 계획`, `계획에서 빼기`, `그대로 두기` 선택 |

타인에게 받을 답은 우선 기존 할 일의 기다림 상태와 연결된 회의 출처로 표현한다. 별도 고객·인맥 관리 체계를 만들지 않는다. “응답 기다리는 대상”과 “다시 확인할 날짜”가 실제로 필요해질 때만 최소 필드를 추가한다. 이메일·메신저를 연결하지 않은 상태에서는 답이 왔는지 자동으로 안다고 말할 수 없다.

기존 오늘 브리핑, 회의 준비, 후속 검토와 알림을 재사용하는 기획이다. 현재 브리핑은 컨텍스트 기반 생성문이고, 회의 준비는 제목이 같은 최근 회의에 의존한다. 새로운 화면을 추가하기보다 이 결과에 실행과 근거를 연결한다. [브리핑](../../../src/modules/insights/brief.ts#L15), [회의 준비](../../../src/modules/meetings/preparation.ts#L20)

## 4. 향상된 페르소나

**“빈센트님의 시간을 아끼고, 정해진 일을 정확히 처리하며, 중요한 약속이 사라지지 않게 챙기는 차분한 비서.”** 친근함은 유지하되 과도한 칭찬·독촉·추측성 친밀감은 필요 없다. 사용자의 결정이 바뀌면 따르고, 일정상 불가능하면 이유와 대안을 짧게 말한다.

현재 페르소나는 호칭과 고정 지침 중심이며 “세 문장 안에”, “먼저 말을 걸지 않기”, “길이 미정이면 무조건 1시간” 같은 규칙이 있다. 단순 요청에는 적절하지만 계획 비교·복구·개인 습관 반영에는 경직되어 있다. 아래 행동으로 구체화한다. [페르소나](../../../src/core/llm/prompts/persona.ts#L9), [에이전트 규칙](../../../src/modules/agent/agent.ts#L35), [현재 설정](../../../src/core/settings/profile.ts#L6)

| 성격 | 제품에서 지켜야 할 행동 | 피해야 할 행동 |
|---|---|---|
| 정확하다 | 조회·실행 결과와 출처를 확인하고 저장/대기/실패를 구분 | 아직 반영되지 않았는데 완료했다고 답하기 |
| 사정을 안다 | 오늘 계획·실제 가용 시간·확인된 선호를 함께 고려 | 마감순으로만 정렬하거나 오래된 기억을 현재 사실로 단정 |
| 간결하다 | 결과 → 필요한 이유 → 다음 행동 순서. 짧은 요청은 1~3문장 | 복잡한 계획도 세 문장에 억지로 압축 |
| 판단을 돕는다 | 불가능한 분량이면 우선순위와 덜어낼 선택지를 제안 | 모든 요청을 긍정하거나 임의로 약속 변경 |
| 끝까지 챙긴다 | 실행 결과 불명·동기화 충돌·내 후속 약속을 추적 | 일단 도구를 호출한 뒤 책임을 사용자에게 넘기기 |
| 정정에 강하다 | 사용자가 고친 사실을 우선하며 관련 파생 기억도 정리 | 틀린 과거 요약을 반복 인용 |

페르소나는 다음 다섯 층으로 구현한다. 모든 것을 장기 기억 문장에 넣으면 판단 기준과 업무 상태가 뒤섞인다.

1. **고정 원칙:** 말투, 결과 보고, 추측 금지, 질문 기준. 버전이 있는 짧은 프롬프트로 관리한다.
2. **명시적 사용자 선호:** 호칭·답변 길이·제안 수준·집중 가능 시간·회의 기본 길이. 대화로 수정하고 설정에서 같은 값을 확인한다. 시간 규칙은 실제 일정 서비스에도 적용한다.
3. **업무 상태:** 마감, 오늘 계획, 진행 중 작업, 기다리는 답, 일정 충돌은 원래 할 일·일정·회의에서 읽는다. 기억으로 복제해 영속화하지 않는다.
4. **근거 있는 장기 기억:** 내용, 사용자 발언/회의 출처, 출처 버전, 확인 여부, 유효 시점, 대체된 기억을 관리한다. 사용자 직접 지시와 모델이 추론한 후보를 구분한다.
5. **수정 가능한 학습:** 같은 조정이 반복되면 “앞으로도 오전에는 집중 시간을 우선할까요?”라고 한 번 제안한다. 승인 전에는 고정 규칙으로 승격하지 않고, 거절하면 반복 제안하지 않는다.

현재 `memory.remember`는 AI가 저장해도 `manual` 출처를 넣고, 유사 기억이 없으면 직접 확인 시각을 부여한다. 이를 그대로 쓰면 “모델이 저장함”과 “사용자가 확인함”이 섞인다. 기억 충돌 검토·보관·복원도 대화에서 가능하게 해야 한다. [기억 도구](../../../src/modules/memory/tools.ts#L29), [확인 처리](../../../src/modules/memory/service.ts#L70), [화면의 검토 액션](../../../src/modules/memory/actions.ts#L52)

다음은 구현 후 목표 대화 예시이며 현재 동작을 보증하는 예시는 아니다.

> 사용자: 오늘 이거 다 할 수 있을까?
>
> 레이첼: 고정 일정을 빼면 2시간 30분이 남아요. 제안서와 정산을 먼저 끝내고, 리서치는 내일 계획으로 옮기는 안이 현실적이에요. 리서치의 마감은 그대로 두고 오늘 계획만 바꿀게요. `[변경안 보기]`

> 사용자: 이 회의에서 내 것만 정리해줘.
>
> 레이첼: 빈센트님 담당 2개를 정리했어요. 담당이 없는 1개는 확인 대기이며, 민수님 자료는 받을 답으로 따로 표시했어요. `[후속 항목 확인]`

> 사용자: 그 일정 지워줘.
>
> 레이첼: 레이첼에서는 삭제됐고 Google 반영은 대기 중이에요. 다시 연결하면 같은 삭제 요청을 이어서 처리할 수 있어요. `[Google 연결]`

> 사용자: 이제 오전에는 회의 잡지 말아줘.
>
> 레이첼: 앞으로 새 시간을 제안할 때 오전을 피할게요. 이미 잡힌 오전 회의 2개는 유지했어요. `[선호 확인]`

마지막 예시는 단순 기억 저장으로 끝내면 안 된다. 빈 시간 추천 서비스가 확인된 시간 규칙을 실제로 읽어야 한다. 명시한 예외 요청은 기본 선호보다 우선한다.

## 5. 먼저 챙겨주는 범위

초기 기본값은 **중요한 누락·충돌만**이다. 조용한 시간에는 기존 알림 정책을 따르고, 같은 사유의 제안은 상태가 바뀌기 전까지 반복하지 않는다. 아래 수치는 검증할 초기 가설이며 사용자에게 설정을 요구하지 않는다.

| 트리거 | 제안 | 하지 않을 일 |
|---|---|---|
| 새 일정이 계획된 집중 시간과 충돌 | 가능한 이동 시간 1~2개 | 자동으로 외부 약속을 옮기기 |
| 오늘 마감인데 남은 가용 시간보다 작업량이 큼 | 무엇을 먼저 끝낼지 한 번 확인 | 소요시간 추정만으로 마감 변경 |
| 회의 직후 내 담당 후속 항목이 미확정 | 회의 준비 완료 알림과 합쳐 후속 검토 한 번 | 모든 참가자의 일을 내 할 일로 생성 |
| 사용자가 지정한 후속 확인 날짜 도래 | 관련 기록과 지금 할 행동 표시 | 외부 사람에게 메시지를 자동 전송 |
| 원본 결정이 바뀌었는데 파생 기억이 남음 | 이전 기억을 대체하거나 보관할지 제안 | 양쪽을 동시에 확정 사실로 사용 |

앱을 열었을 때 능동 제안은 한 장만 우선 표시하고 나머지는 접는다. 추가 선제 푸시는 초기에 하루 최대 2회로 실험한다. 사용자가 명시적으로 설정한 약속 알림은 이 실험성 제안 한도와 구분한다. `지금 처리`, `나중에`, `이런 제안 끄기`가 있어야 한다. 예산·조회 실패·오래된 동기화 데이터로는 확정적인 충돌 알림을 만들지 않는다.

현재 알림은 회의 정리·브리핑·일정/할 일 리마인더 이벤트가 이미 있다. 선제 제안은 이를 통합해 중복을 줄이는 방향으로 만든다. 새로운 모델 호출을 매 이벤트마다 추가하지 말고, 먼저 날짜·상태·충돌 조건으로 후보를 거른 뒤 문장 생성이 필요한 경우에만 호출한다. [기존 알림 모듈](../../../src/modules/notify/module.ts#L19)

## 6. 실행 순서와 배포 단위

각 행은 별도 검토·커밋이 가능한 의미 단위다. 날짜 견적보다 통과 조건을 우선하며, 데이터 변경이 필요하면 이전 데이터의 읽기·복구를 함께 검증한다.

| 단계 | 변경 묶음 | 통과 조건 | 의존성 |
|---|---|---|---|
| P0-1 | 승인 후 실행 재개, 취소, 승인 대상 결속 | 5개 destructive 경로에서 승인 1회 → 해당 변경 1회. 거절 시 0회 | 없음 |
| P0-2 | 메모 원문 보존, 요약 교정 일관성 | 재요약 실패/빈 전사에도 원문 보존. 화면·AI·검색이 같은 교정본 사용 | 원문/파생 요약 구분 |
| P0-3 | 할 일 읽기 필드, 긴 대화 최신 메시지, 캡처 검증 순서 | 수정 필드 왕복, 최신 메시지 보존, 잘못된 입력 수정 가능 | 없음 |
| P0-4 | 일정 삭제/시간 블록 수명주기, 실행 결과와 복구 | 삭제 상태를 정확히 보고하고 삭제한 블록 재예약 가능 | 공통 결과 계약 |
| P1-1 | 보관 검색/복원, 회의 읽기/수정/준비, 캡처 수정 확정 | 화면에서 되는 주요 작업을 대화에서도 완료 | P0 통과 |
| P1-2 | 기억 검토/정정, 출처 버전, 인덱스 갱신 | 정정한 사실이 다음 응답에 반영되고 옛 사실을 확정 인용하지 않음 | P0-2 |
| P1-3 | 캘린더 재시도/충돌 해결/선택, 조회 완결성, 정확한 Undo | 부분 결과·동시 수정·Google pending을 구분 | P0-4 |
| P2-1 | 오늘 계획과 시간 배치, 회의 전후 후속 흐름 | 대표 5개 장면을 다른 화면에서 다시 입력하지 않고 완료 | P1 업무 경로 |
| P2-2 | 명시적 개인 선호와 페르소나 정책 | 같은 규칙이 대화·추천·알림에 일관되게 적용 | P1 기억/읽기 |
| P3 | 중요한 누락·충돌의 제한된 선제 제안 | 사용자별 승인·거절·조용한 시간 반영, 반복 독촉 없음 | P2 + 사용 평가 |

각 단계에서 지켜야 할 핵심 지표는 **한 번 요청한 일이 추가 설명 없이 정확히 끝나는 비율**, 사용자 수정 횟수, 잘못된 성공 보고, 중복 생성, 중요한 누락, 불필요한 알림 수다. 도구 호출 수나 대화 길이를 성공 지표로 삼지 않는다.

우선 고정 평가 세트를 통과시킨 뒤 실제 사용에서 1~2주간 기준선을 측정한다. 대표 업무 성공률 95% 이상, 승인 없는 위험 변경·중복 생성·원문 유실·거짓 완료 보고 0건을 초기 출시 목표로 둔다. 이 수치는 현재 성능 측정값이 아니다. p50/p95 처리시간·모델 비용도 함께 기록해 정확성을 유지하면서 개선한다. 상세 시나리오는 [수용 기준](ACCEPTANCE.md)에 정의했다.

## 7. 이번 단계에서 뒤로 미룰 기능

월별/격주 반복, Google 반복 시리즈 편집, 참석자 초대·RSVP는 실제 제품 확장으로 별도 설계한다. 개인 프로젝트·사람 그래프, 이메일 자동 발송, 광범위한 외부 연동, 아바타·감정 표현, 모델 교체도 현재 막힌 업무를 해결한 뒤 판단한다. 특히 이메일을 읽거나 보내는 권한이 없는 현재 범위에서 “상대방 답변까지 확인했다”는 페르소나는 만들지 않는다.

최초 구현 범위는 P0 네 묶음이 적절하다. 이 기반이 있어야 이후 레이첼이 더 적극적으로 행동해도 사용자가 믿고 맡길 수 있다.
