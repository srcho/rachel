# 기획 수용 기준과 검증 순서

기준: 2026-09-05 기획안. 아래는 **앞으로 구현 후 충족해야 할 조건**이다. 현재 통과 결과가 아니다. 현재 결함 재현은 [AUDIT](AUDIT.md#3-로컬에서-재현한-결함)의 별도 진단 7개로 구분한다.

## 검증 계층

1. 서비스·DB 계약: 로컬 격리 사용자, 실제 저장 결과/영향 행 수 검증. 외부 API는 실패·시간초과·충돌을 주입한다.
2. 도구 계약: UI와 도구의 같은 입력이 같은 결과를 내는지 비교한다. 출력 필드·승인·실행 기록·Undo까지 포함한다.
3. 브라우저: 승인 클릭, 새로고침, 중단 후 재개, 모바일 카드, 키보드 조작을 확인한다. 성공 문구만 보지 않고 실제 데이터와 대조한다.
4. 실제 Luna: 고정 평가 데이터와 시각으로 같은 요청을 반복하고 도구 선택·인자·최종 보고·질문 수를 평가한다. 모델 테스트 실패는 서비스 실패와 분리한다.
5. 실제 연동: 테스트용 Google 캘린더·기기 권한·알림에서 동기화와 재연결을 확인한다. 운영 개인 데이터를 실험 대상으로 쓰지 않는다.

## 합격 판정

- P0 단계는 관련 결정적 회귀 테스트가 전부 통과하고 브라우저에서 해당 경로가 실제 데이터와 일치해야 한다. 진단 코드의 잘못된 동작을 새 테스트의 기대값으로 사용하지 않는다.
- 실제 Luna 평가는 핵심 요청을 최소 3회 반복하고 고정 데이터·시각·모델·프롬프트 버전을 기록한다. 목표는 대표 업무 성공률 95% 이상이다. 시나리오 난이도와 시행 수를 함께 공개한다.
- 원문 유실, 승인 없는 위험 변경, 다른 사용자 데이터 접근, 중복 생성, 거짓 완료 보고는 평가 세트에서 0건이어야 한다. 일부 평균 점수로 상쇄하지 않는다.
- 의도적으로 거절해야 하는 요청은 “정확하게 거절하고 가능한 다음 행동 제시”를 성공으로 친다. 지원하지 않는 시리즈 편집을 수행한 척하는 것은 실패다.
- 통과 결과에는 서비스/도구/Luna/브라우저/외부 연동 중 무엇을 검증했는지 명시한다. 로컬 테스트 통과를 운영 Google·음성·푸시 검증으로 확대 해석하지 않는다.

## 실제 사용 평가

1~2주 개인 사용 기간에 요청 단위로 시작/종료, 결과 ID, 추가 설명 횟수, 사용자 정정, 재시도·중복, 제안 승인/거절/무시를 기록한다. 원문 대화를 무제한 쌓는 대신 필요한 사건과 버전을 우선 기록한다.

| 지표 | 정의 | 초기 목표/사용법 |
|---|---|---|
| 요청 완료율 | 지원 대상 요청 중 올바른 자원 상태로 끝난 비율 | 95% 목표. 현재 수치 아님 |
| 추가 설명 부담 | 요청당 사용자가 다시 대상·날짜·조건을 설명한 횟수 | 현행 기준선 대비 감소 |
| 잘못된 완료 보고 | 미완료/외부 pending/0행 변경인데 완료라고 답한 건수 | 0건 |
| 원문 유실·중복·무단 변경 | 직접 데이터 대조로 확인 | 0건 |
| 제안 효용 | 처리/수정 후 처리/거절/무시 비율과 이유 | 승인율만 최적화하지 않고 방해 횟수도 함께 판단 |
| 처리시간·비용 | 업무별 p50/p95 지연, 요청당 모델 비용 | 정확성을 유지하며 기준선보다 개선 |

지표가 좋아도 사용자가 “확인할 일이 오히려 늘었다”고 느끼면 제안 빈도와 확인 절차를 줄인다. 새로운 설정을 추가하기 전에 불필요한 개입부터 제거한다.
